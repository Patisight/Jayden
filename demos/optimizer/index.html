01

它解决什么问题/ The Loop

人工调天线的时间，一半花在「改一个数、等一次求解、看一眼曲线」这件事上。

贴片天线的回波损耗、增益、辐射效率、端口隔离由几何尺寸决定，而这些指标互相掣肘： 把馈电点挪到 S11 最低的位置，往往正是增益最差的位置。手工调参是在这条权衡面上凭经验打转， 而每打转一次都要付出一整次全波仿真的时间。

这套工具做的事，是把 HFSS 从「人操作的软件」变成「程序调用的求解器」。 闭环的四个环节都能在源码里逐一对上： 参数写入是 HFSSController.set_variable(name, value, unit)， 求解是 analyze() 后接 _verify_analysis_ran() 确认这一轮真的算完了， 取值是 get_s_parameters() / get_gain_3d() / get_antenna_efficiency() （取远场量时若工程里没有远场球面，由 _ensure_far_field_sphere() 现场建一个）， 评估则由 evaluator 把公式解析成目标向量并判定是否达标。

一条公式 f(x) = dB(S(1,1)) 在界面上只是一行文本，落到执行层是一次正则匹配 + 一次报表取数 + 一次频段内极值归约：目标配置里的 constraint 决定这一步取 max 还是 min， 默认取 max——回波损耗要压的是「频段内最差的那一点」。 Peak(Gain) 这类写法走的则不是报表曲线，而是远场三维数据里搜全局最大增益。

优化循环本身不碰 HFSS，它只跟 evaluator 要一批解的目标值。 evaluator 才是真正干活的地方：多进程评估器为每个 .aedt 副本起一个独立 HFSS 进程， 把一代种群切成子任务分发下去，从结果队列收解；某个 worker 挂了会被重启并把剩余任务重新入队。 这就是界面上「并行 HFSS 进程」那一栏的意义——它不是可选项的装饰， 而是把 500 次求解的墙钟时间按比例砍下来的主要手段。

还有一处不起眼的实现细节值得说：HFSS 会把每次求解的结果缓存在工程文件里， 几百次求解之后内存与磁盘都能把它撑爆。所以控制器专门留了 clear_solution_cache() 与 cleanup_solutions()， 评估器按「每 N 次仿真清理一次」的节奏定期回收——长任务能不能跑完，很多时候就取决于这一步。

每一次评估都以 JSON Lines 追加写入 evaluations.jsonl：参数向量、逐目标的 value（优化空间值）、actual_value（物理值）与 goal_met（是否达标）。 全部种群跑完后，非支配解写进 results.json，连同这一轮的配置快照落在 optim_results/算法名_时间戳/ 目录下。界面上「结果分析」看到的每一条，就是这里的一个目录。

02

六个面板分别对应什么/ Panels & Endpoints

左侧导航不是一般意义上的「页面切换」，它按的就是优化任务的配置顺序。

整个界面是一份配置的六个切面，共用同一个 /api/config 文档； 「保存配置」把整份对象 POST 回去，后端落盘为 user_config.json。 命令行 run.py 读的就是这同一份文件—— Web 界面只是编辑器，跑任务的从来不是它。这也是为什么界面上没有「实时预览仿真」这类按钮。

01 项目配置
GET /api/templates · GET /api/browse · GET|POST /api/config模板卡 + .aedt 路径 + 设计/设置/扫频名 + 并行路径表
02 优化变量
POST /api/config → variables[]{name, bounds[2], unit}边界可填公式引用其它变量，由约束求解器按依赖序展开
03 优化目标
POST /api/config → objectives[]{name, formula, freq|freq_range, goal, target, weight}方向只有最小化 / 最大化两种，权重用于标量化路径
04 算法配置
GET /api/algorithms单选算法 + 详情描述（全称 / 适用目标数 / 优势 / 局限 / 最佳场景）+ 专有参数面板
05 运行控制
POST /api/start · POST /api/stop · GET /api/status（1 s 轮询）进度条 = progress / total，日志滑窗 50 行，错误可展开 traceback
06 结果分析
GET /api/results · GET /api/results/{name}历史运行目录列表 → 非支配解卡片：参数 + 各目标 actual_value

面板之间是有耦合的

「算法配置」那一栏里随算法而变的专有参数最容易被忽略：选 MOPSO 出现惯性权重上下限与两个学习因子， 选 MOEA/D 出现权重向量分区数与邻域大小 θ，选 NSGA-III 出现参考点分区数，选 CMA-ES 只剩一个初始步长 σ₀。 这不是界面花活——这些参数只有对应算法才消费。

「优化变量」的边界支持公式（例如 (Wc-Wm2)/2+0.01）， 于是变量不再是彼此独立的矩形搜索空间：结构对称、避免干涉、相邻尺寸必须小于某个比例 这类几何约束能直接写进边界，由约束模块解析依赖顺序后展开成实际取值范围。 不做这件事，优化器会花掉大量求解次数去评估物理上根本不成立的几何。

「运行控制」的错误处理也照实反映后端：启动前会校验项目路径必须是绝对路径且文件存在、 变量与目标都不能为空，否则直接拒绝启动；手动停止时设置停止事件，该信号一路传到 pymoo 回调、进度回调和 worker 进程，界面随即显示「用户手动停止」。

03

为什么要多目标算法与代理模型/ Algorithms & Surrogates

一次求解要几分钟，一次任务要几百次——这两句话决定了整套算法选型。

加权求和不能替代多目标算法。把 S11 与增益按权重压成一个标量，确实能让单目标优化器正常工作， 但一次只能得到一个折中点，换权重就要从头再跑几百次仿真；而且权重与最终解的对应关系是非线性的， 前沿有非凸段时某些解无论怎么调权重都取不到。多目标算法反过来：一次运行直接交付一整条 Pareto 前沿，工程师拿到的不是「一个答案」，而是「这套尺寸换那 0.3 dB 增益值不值」的完整菜单。

实现上所有目标都被统一到「越小越好」：最大化目标在优化空间里取负， 于是支配判断只需逐维比较。界面上看到的 actual_value 再翻回物理值， 所以「PeakGain 6.42 dB」和「优化器内部的 −6.42」是同一个数的两面—— 结果卡片同时保留这两个字段，画图时用的是前者。

七个算法不是给选择困难症准备的，它们各自对应不同的目标维度与前沿形状： 超体积驱动的几何自适应、参考点引导、分解成标量子问题、角度惩罚距离—— 目标一多，「非支配排序 + 拥挤距离」这条老路会因为几乎人人互不支配而失效， 这正是 NSGA-III、RVEA 存在的理由。

早停
另一个只在真实代价下才成立的设置是达标即停：档案里已经有足够多个非支配解 同时满足所有目标值时，剩下的仿真预算就没有意义了。界面上的「达标解数量」就是这个阈值， 算法每代检查一次，达到即 break——所以演示里那次合成任务的进度条不会走满， 它通常在预设迭代数的五到八成之间就停住，日志里会打出 Early stop: n solutions meet goals。

代理模型：把仿真次数从预算里买回来

多目标算法把「一次调参」变成「几百次求解」，代价立刻从方便变成跑不完。 代理模型是这条链路上唯一的减速带反向操作： 用已经仿真过的点训练一个廉价预测器（配置里 use_surrogate 打开， surrogate_type 指定模型族），让优化器先在预测面上大面积搜索， 只把最有希望的少数候选送进 HFSS 做真仿真，新得到的真值再回填训练集。

这套双线结构必须让结果可信度可区分，所以每个解都带 is_predicted 标记，统计里 n_evaluations 与 real_evaluations 分开记账，画图时预测点与实测点分色。 一份报告里同时存在两种置信度的点，如果不标注，就是错的。

代理模型本身会错，尤其在训练点稀疏的角落。所以「预测值」不能直接当成结论用—— 前沿上真要用那个尺寸做样机，得把它送回 HFSS 复算一次。界面上把这一点交给结果分析与实测流程， 而不是在优化过程中偷偷替工程师做主。

04

这份演示的边界/ What Is Real

界面是真的，数字是编的。分不清这句话，就会被演示骗到。

真实
界面 与结构

Vue3 + Element Plus 的控制台照搬源项目 web/index.html，面板、字段、校验、轮询节奏、日志措辞都未改动。

真实
契约 与字段

14 个接口的响应结构按 server.py 的路由与 Pydantic 模型对齐：变量用 bounds，目标用 actual_value，列表限 20 条。

合成
全部数值

项目路径、变量边界、目标值、迭代进度、Pareto 解、历史运行记录都是垫片现编的，没有任何一次真实求解。

垫片做的是同源请求拦截：源前端里 const API = ''，所有请求写成相对路径， 本来就指向「同一个站点下的后端」。演示页把这个地址换成了本地生成的 JSON， 因此这份 app 文件放回源项目的 web/ 目录、或在 window.__DEMO_MOCK__ 关掉之后，就能直接对着真的 FastAPI 服务跑—— 不需要改一行界面代码。

有两处刻意与真实后端不一致：其一是文件浏览，真接口会弹一个操作系统原生对话框， 网页里不可能有，垫片改为轮流返回几个占位路径；其二是模板列表， 真实接口只回名称与变量/目标个数，前端却指望列表里带着完整变量与目标才能套用模板， 演示里补上了这两个字段，否则「加载模板」点了没反应。两处都写在 app 文件顶部的注释里。

要跑真的需要什么

  • 本机 Ansys HFSS 与许可证，以及 PyAEDT 能连上的版本hardware
  • 一个参数化好的 .aedt 工程：待优化的尺寸必须是 HFSS 里的命名变量，否则 set_variable 无处可写
  • 已配置的目标报表：S 参数、远场球、增益与效率都得在工程里能取到数
  • pymoo（可选）：AGE-MOEA2 / NSGA-III / MOEA/D / RVEA 走的是它optional
  • python server.py，然后浏览器打开本机服务端口localhost
